# 01 定位与范围

## 一、要解决的问题

RAGFlow、WeKnora 一类平台的资源门槛主要来自“运行时底座”，而不是检索算法本身：

| 开销来源 | 典型组件 | 性质 | TuskRAG 的处理 |
|---|---|---|---|
| 搜索引擎 JVM 堆 | Elasticsearch | 常驻、需预留 | 用 PostgreSQL 内的 BM25 + pgvector 替代（[A01](11-架构决策记录.md#a01)、[A03](11-架构决策记录.md#a03)） |
| 多中间件待机 | MySQL、Redis、MinIO、Nginx、MQ | 常驻、固定成本 | 全部收敛到单个 PG + 本地盘/已有对象存储（[A01](11-架构决策记录.md#a01)、[A15](11-架构决策记录.md#a15)） |
| 重量级解析套件 | LibreOffice、Playwright、本地 OCR | 低频但常驻 | 原生轻量库 + 页级质量门 + 按需 VLM；重组件只作为可选的一次性进程（[A06](11-架构决策记录.md#a06)、[A07](11-架构决策记录.md#a07)） |
| 本地大模型 | Ollama 7B/8B | 常驻、大块内存 | 核心进程不加载模型；统一走 OpenAI 兼容接口，离线时由独立模型节点提供（[A05](11-架构决策记录.md#a05)） |
| 企业级冗余 | 分布式集群预设 | 架构预付 | 同一制品按角色水平扩展，单机档位不预留集群冗余（[A02](11-架构决策记录.md#a02)） |

决定“准”的是解析结构完整度、分块与上下文保留、混合检索 + 重排、检索策略四件事；它们都不依赖大块常驻内存。因此 TuskRAG 的核心判断是：**砍掉运行时底座的常驻成本，把节省的复杂度投入到解析质量、重排和评测上。**

## 二、产品定位

- **是**：企业内部知识检索与问答底座；Agent 的“知识工具层”（REST 检索 API + MCP 工具）；带检索调试与评测的知识运营控制台。
- **不是**：通用 Agent 编排平台、工作流画布、LLM 推理服务、搜索引擎爬虫、BI 系统。

## 三、量化目标（目标值，待测量）

测量口径：Linux x86_64，lite 档位（单机 2 vCPU / 4 GB），模型全部外置，PG 与应用同机；20 万子块、1024 维 halfvec。测量方法与门槛见 [10](10-评测与质量保障.md) 与 [09](09-部署运维与可观测.md#六容量规划)。

| 维度 | 指标 | 目标 |
|---|---|---|
| 轻 | 常驻服务数 | 2（postgres、tuskrag） |
| 轻 | 空载常驻内存（PG + 应用，不含 OS 页缓存） | ≤ 0.9 GB（其中 Go 核心 ≤ 80 MB） |
| 轻 | 入库峰值内存（单个 200 页数字 PDF） | 额外 ≤ 600 MB，结束后回落 |
| 快 | 仅数据库的混合召回（过滤 + BM25 Top50 + 向量 Top50 + RRF） | p95 ≤ 100 ms |
| 快 | 完整检索（含外部查询嵌入与 Top50 重排） | p95 ≤ 800 ms |
| 快 | 问答首个 token（外部 LLM 正常时） | p95 ≤ 3 s |
| 快 | 原生解析入库（50 页数字 PDF，至可检索） | ≤ 30 s（不含嵌入 API 排队） |
| 准 | 见 [10 第三节](10-评测与质量保障.md#三指标与门槛) | 以评测集基线为准，回归不超过阈值 |
| 并发 | 同时在线问答 | 50 会话（瓶颈应在外部模型配额，而非本服务） |

## 四、非目标（v1 不做）

1. 不内置或托管 LLM/Embedding/Rerank 推理；离线部署由独立模型节点提供 OpenAI 兼容接口。
2. 不做亿级文档、跨地域多活；单库目标规模为 ≤ 500 万子块（超过即触发 [A01 重审](11-架构决策记录.md#a01)）。
3. 不默认启用 GraphRAG、知识图谱、Contextual Retrieval；只有评测证明增益后才进入路线。
4. 核心不包含 JS 渲染网页抓取（Playwright）；仅支持静态 HTML 与上传文件。
5. 不提供 SQLite/嵌入式轻量模式；开发、测试与生产使用同一 PG 镜像。
6. 不做通用 Agent 编排；Agentic 检索只服务于“回答知识问题”。

## 五、用户角色

| 角色 | 主要任务 |
|---|---|
| 平台管理员 | 租户与身份源配置、模型提供方、数据出域策略、系统状态与审计 |
| 知识库管理员 | 创建知识库、成员与权限、分块/检索配置、评测集维护 |
| 编辑者 | 上传/更新/删除文档、查看解析报告、修正解析问题 |
| 使用者 | 在控制台检索与问答，查看引用原文，提交反馈 |
| 集成方 / Agent | 用范围化 API Key 调用检索 API 或 MCP 工具 |

## 六、对原始分析的修正

原始分析的方向成立，但以下口径在企业落地前必须修正，否则会在许可证、内存或准确率上踩坑：

| 原始说法 | 问题 | 修正后的口径 |
|---|---|---|
| `pg_search` 直接替代 Elasticsearch | ParadeDB Community 为 **AGPL-3.0**；多数云托管 PG（RDS 等）无法安装该扩展 | 默认驱动用 pg_search（含 Jieba 中文分词），同时提供“应用侧分词 + tsvector”兼容驱动；M0 先过法务评估（[A03](11-架构决策记录.md#a03)） |
| 用 `PyMuPDF4LLM` 解析 PDF | PyMuPDF 系列为 **AGPL-3.0/商业双许可**，企业分发有义务 | 默认使用 pypdfium2 / pdfplumber 等宽松许可库；PyMuPDF 仅在已购商业许可时作为可选驱动（[A06](11-架构决策记录.md#a06)） |
| FastEmbed 跑 BGE-M3 + BGE-Reranker-v2-m3 仅约 600 MB | 两者各约 5.7 亿参数，单个 INT8 约 0.6 GB、FP32 约 2.2 GB；FastEmbed 官方支持列表未列出这两个模型；其列出的 jina-reranker-v2 为 **CC-BY-NC**（不可商用） | 核心不加载模型；本地 CPU 推理改为独立模型服务（如 TEI/Xinference），预算按 1.5—3 GB 规划并实测（[A05](11-架构决策记录.md#a05)） |
| `UNLOGGED TABLE` 替代 Redis 做缓存与队列 | UNLOGGED 表在崩溃后被截断、不进入复制 | 只用于可丢失缓存；队列与任务状态使用普通表 + `FOR UPDATE SKIP LOCKED`（[A12](11-架构决策记录.md#a12)） |
| C/Rust 原生引擎“不会 OOM、优雅降级” | PG 同样会因 `work_mem × 连接数`、HNSW 构建等耗尽内存 | 通过连接池上限、`work_mem`、维护窗口内建索引和容量公式控制；以压测证明（[09](09-部署运维与可观测.md)） |
| 2 核 4G 支撑 50 人并发 | 只有在 LLM/嵌入/重排全部外置时才可能成立；瓶颈转移到外部配额与 SSE 连接 | 列为待测目标；压测场景 V09 |
| Agentic 目录树检索“更准” | 多步 LLM 调用增加延迟与成本，与“快”冲突 | 默认单轮混合检索；Agentic 为显式模式或由外部 Agent 经 MCP 驱动（[A10](11-架构决策记录.md#a10)） |
| 扫描件统一走云端 VLM | 文档内容出域，部分企业不允许 | 按知识库配置数据出域策略；不允许时使用内网 VLM 节点或拒绝并提示（[A16](11-架构决策记录.md#a16)） |
| 彻底抛弃 LibreOffice | `.doc/.ppt/.xls` 旧格式没有成熟的纯原生解析 | 默认拒绝旧格式并提示转换；可选启用一次性转换进程，转换完即退（[A06](11-架构决策记录.md#a06)） |
| HNSW 索引只占少量内存 | 索引要放进缓存才快；100 万 × 1024 维 float32 原始向量即约 4 GB | 使用 halfvec（减半），按 [04 容量公式](04-数据模型与存储.md#六容量估算) 规划 `shared_buffers` |
