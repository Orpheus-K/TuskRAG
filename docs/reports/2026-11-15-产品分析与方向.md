# TuskRAG 产品分析报告：亮点、赛道方向与值得扩展的研究功能

> 日期：2026-11-15。性质：产品分析与建议，**不是需求、决策或验收文档**；文中建议在进入 [02 需求与验收](../02-需求与验收.md) 和 [11 架构决策记录](../11-架构决策记录.md) 之前均不代表已支持或已承诺的能力。
>
> 依据：仓库文档（01、02、06、11、12）、[项目笔记](../../.agents/NOTES.md)、[评测报告](../eval-reports)，以及公开的研究与行业资料（见第七节）。外部资料只读了摘要与公开页面，竞品细节未逐项实测。
>
> 对题目的理解：“互联网落地企业这条赛道”按“面向企业交付落地（to-B）的 RAG / 企业知识赛道”理解。

## 一、结论摘要

1. **TuskRAG 的产品亮点不在检索算法，而在“可交付性”**：两个常驻服务、权限正确性可证明、失败显式暴露、质量可评测。这四点正好对应企业知识库“能答了却不敢上线”的原因（怕串权限、怕答错、怕说不清质量）。
2. **最适合的赛道位置是“Agent 的带权限知识工具层”**，而不是再做一个 Dify / RAGFlow 式的平台。建议主线为：被 Agent 平台和业务系统集成（MCP / REST / OEM），以强合规行业的部门级私有化为切入点。
3. **当前最大的产品缺口是数据接入，不是检索**：只有文件上传和静态 URL 导入，没有企业内容源连接器和源端权限同步。这一项不补，其他优势难以兑现。
4. **研究方向中优先级最高的四项**：MCP 用户委托授权（OAuth）、检索投毒与间接提示注入防护、Agentic 检索的停止与路由（现有实测暴露了问题）、评测闭环（自动出题与线上反馈回流）。Contextual Retrieval 和视觉文档检索值得做受控实验；GraphRAG 继续保持观望。
5. **若干对外口径尚不能承诺**：真实客户语料上的准确率、50 并发下的首 token 延迟、百万块规模延迟、pg_search 的 AGPL 法务结论。详见第三节。

## 二、产品亮点

以下每条都区分“已有实测证据”与“仅为设计”。

### 2.1 部署与持有成本低（已实测，有偏差项）

| 指标 | 目标 | 实测（20 万块，假模型，2 vCPU 档） | 结论 |
|---|---|---|---|
| 常驻服务数 | 2 | 2（PostgreSQL + Go 核心） | 达成 |
| 空载内存合计 | ≤ 0.9 GB | 约 774 MiB | 达成 |
| Go 核心空载 | ≤ 80 MB | 102.4 MiB | **未达成** |
| 50 并发峰值合计 | lite 档 4 GB 内 | 约 1.07 GiB | 达成 |

数据来自 [压测报告](../eval-reports/2026-11-15-v08-v09-t17-benchmark.md)。

产品含义：一次备份、一个事务边界、一个 DBA 熟悉的数据库。对比同类产品通常需要的搜索引擎、缓存、对象存储和消息队列，这是交付和运维成本上的实质差异，也是部门级预算能够承受的规格。

### 2.2 权限正确性是一等公民（已实测）

- 检索前预过滤、出库前复核、撤权即时生效，流式回答进行中也会复核（[A11](../11-架构决策记录.md#a11)）。
- REST、MCP、调试台、问答共用同一服务层，权限一致性有专门验证（T08—T11、V14）。
- 所有评测报告以“越权证据数为 0”作为硬门禁。
- 工程深度的一个例证：发现 pg_search 通用计划在租户切换后会复用旧租户条件，并以强制自定义计划加就绪检查封堵（[A03](../11-架构决策记录.md#a03)）。

产品含义：多数开源 RAG 平台的权限停留在知识库级别，文档级权限和撤权时效通常说不清。TuskRAG 能给出可复现的证据，这是面向安全与合规评审时最有说服力的卖点。

### 2.3 不伪装成功（已实现）

- 降级必须出现在响应的 `degraded` 字段，重排失败不会把融合分数冒充重排分数。
- 引用逐条校验，无有效引用的回答标记 `unsupported`；证据不足时拒答且不带引用。
- 质量门不达标的页面显式失败或标注“部分可用”，不静默入库。

产品含义：企业用户对“答错但看起来对”的容忍度远低于“明确说不知道”。这一点很难从演示中看出来，但决定了上线后的信任。

### 2.4 评测内建于产品（已实现）

控制台内有题集管理、固定修订运行、报告对比和两个百分点的回归门禁；生成侧有引用准确率、拒答准确率等指标。

产品含义：把“准确率”从口头承诺变成可签入合同的验收项。同类产品大多把评测留给用户自己搭建。

### 2.5 知识生命周期完整（已实测）

- 文档新版本就绪后原子切换，失败版本不影响当前版本。
- 更换嵌入模型时后台重建、完成后原子切换，期间旧空间继续服务（T13）。
- 软删除、清理任务可见可重试，崩溃后任务可恢复且无重复块。

产品含义：解决“知识过期”和“换模型要停机重灌”两个长期运营痛点。

### 2.6 数据出域策略可强制、可审计（已实现）

按知识库配置出域策略，所有模型调用经单一入口检查（[A16](../11-架构决策记录.md#a16)）。扫描件在禁止出域时不会被送往外部 VLM。配合模型全部外置，天然适配内网模型网关。

### 2.7 为 Agent 准备好的接口（已实现）

MCP Streamable HTTP 提供检索、列文档、读目录、读节、读相邻块等工具，范围化 API Key 带限速和配额。目录与读节工具让外部 Agent 可以按文档结构导航，而不仅是拿到碎片。

### 2.8 许可与供应链意识（部分完成）

项目自身为 MIT；主动避开 AGPL 的 PyMuPDF；有 SBOM 脚本。遗留风险见 3.4。

## 三、不能回避的短板与未证实项

### 3.1 数据接入能力弱

只有上传和静态 URL 导入。没有飞书、钉钉、企业微信、Confluence、SharePoint、网盘、工单系统等连接器，也没有源端权限同步和增量同步。企业知识的主体在这些系统里，不在待上传的文件夹里。

### 3.2 准确率证据不足以对外承诺

- 真实模型基线只在 64 题合成中文题集上运行，整文档夹具仅 12 个可见块，不同 Top-N 的候选相同，[基线报告](../eval-reports/2026-10-29-real-baseline.md) 自己也说明不能代表客户语料。
- 开发计划要求的“至少两个真实脱敏知识库”尚未到位。
- 复杂版面（多栏、无线表）在原生解析路径上质量有限，这是设计上已承认的代价（[A06](../11-架构决策记录.md#a06)）；VLM 重解析的验证只覆盖 2 页样本。

### 3.3 性能目标有三处未达成

| 目标 | 实测 | 说明 |
|---|---|---|
| 完整检索 p95 ≤ 800 ms | 真实模型下约 1.0—1.3 s | 瓶颈在外部嵌入与重排 |
| 首 token p95 ≤ 3 s，50 会话 | 50 并发下首 token p50 4.39 s、p95 4.85 s | 使用假模型，即外部模型耗时为零时仍超标 |
| 百万块 SQL 召回 p95 ≤ 100 ms | 271.9 ms | 20 万块为 85.0 ms，已达标 |

第二项需要特别注意：50 个同时在途的请求比“50 个在线会话”更严苛，但这一结果说明 2 vCPU 档位的排队瓶颈在本服务与数据库，而不是定位文档所预期的“瓶颈应在外部模型配额”。对外口径需要改写，或者明确 lite 档的并发上限。

### 3.4 许可风险未关闭

默认词法驱动 pg_search 为 AGPL-3.0，法务意见尚未取得。兼容驱动（tsvector）在真实模型评测中词法 MRR@10 下降约 6.6 个百分点，超过回归门槛；重排后在小题集上持平，但小题集不足以下结论。

### 3.5 Agentic 模式的实测结果不理想

[E7 报告](../eval-reports/2026-11-14-e7-agentic-and-mcp.md) 的 4 道题中，Agentic 模式全部跑满 6 步并被截断，平均耗时约为标准模式的 3 倍，命中率没有提升。这说明当前循环缺少有效的停止判断，而不只是“小语料上标准模式更优”。

### 3.6 其他未验证项

跨版本滚动升级（V13）、连接池代理下的计划缓存安全、Windows 完整沙箱、发行版镜像扫描均未运行。跨知识库检索在 [06](../06-检索与问答.md) 中仍记为未完成。

## 四、赛道判断

### 4.1 赛道现状

- **平台型产品已经拥挤**。Dify 代表编排广度，RAGFlow 代表解析深度，WeKnora 以 MIT 许可和易上手切入，MaxKB、Coze 等各占一角（见 [2026 选型对比](https://ones.com.cn/tools-curated/ai-knowledge-base-tools-comparison-2026)）。在画布、解析模型、生态插件上追赶没有胜算，也违背 TuskRAG 的非目标。
- **检索正在从“应用”下沉为“Agent 的工具”**。MCP 成为事实接口；同时出现“Agent 直接用 grep 检索”的趋势，说明 Agent 需要的是多种可组合的检索工具，而不是一条固定流水线（见 [相关讨论](https://cloud.tencent.cn/developer/article/2663036)）。
- **企业级检索的门槛在权限与新鲜度**。Glean 一类产品的核心资产是连接器、实时权限同步和权限漂移检测。国内落地讨论的痛点同样集中在串租户、答错和知识过期（见 [企业知识库落地讨论](https://cloud.tencent.cn/developer/article/2763925)）。

### 4.2 可选方向与取舍

| 方向 | 内容 | 与现有优势的契合 | 主要缺口 | 建议 |
|---|---|---|---|---|
| A 带权限的知识工具层 | 作为 Dify、Coze、自研 Agent 的外部知识后端，经 MCP / REST 接入 | 高：权限一致性、MCP、范围化 Key 已有 | 用户委托授权、主流平台的外部知识库协议适配 | **主线** |
| B 被业务软件内嵌（OEM） | 供 OA、客服、ERP、行业 SaaS 厂商内嵌 | 高：单二进制、MIT、租户隔离、资源占用低 | 嵌入式管理接口、白标、AGPL 结论 | **主线** |
| C 强合规行业的部门级私有化 | 金融、法务、制造、政务等内网场景 | 高：出域策略、审计、引用、拒答 | 真实语料评测、扫描件与复杂版面、行业样板 | **切入点** |
| D 托管 PG 上的轻量部署 | 在云厂商托管 PostgreSQL 上运行 | 中：兼容驱动已有 | 兼容驱动的质量损失需要量化 | 作为 C 的部署选项 |
| E 自有 SaaS | 多租户公有云服务 | 中：租户隔离已有 | 计费、运营、合规资质，2 人团队难以承担 | 暂不做 |
| F 通用 Agent / 工作流平台 | 画布与编排 | 低：明确的非目标 | — | 不做 |

国产数据库适配（信创要求）是 C 方向可能遇到的问题：pgvector 与 pg_search 在各国产 PG 系数据库上的可用性未经验证，在出现具体客户要求前不应承诺。

### 4.3 建议的定位表述

> 给企业 Agent 用的、权限可证明的轻量知识检索底座：两个服务即可私有部署，每条证据都有出处，每次越权都是零。

三条差异化主张，以及每条需要补齐的证据：

| 主张 | 现有证据 | 仍需补齐 |
|---|---|---|
| 轻 | 20 万块下合计峰值约 1.07 GiB | Go 核心空载超标的原因；入库峰值的测量 |
| 权限可证明 | 越权证据数 0 的全量门禁，撤权与一致性测试 | 源端权限同步；第三方安全评审 |
| 质量可验收 | 评测中心与回归门禁 | 真实客户语料基线 |

### 4.4 推进顺序建议

1. **先关闭对外口径的缺口**：真实语料评测、AGPL 法务结论、并发口径修订。这些不需要新功能，但决定能否签第一单。
2. **补齐接入**：两到三个国内主流内容源的连接器，带增量同步和权限映射。按现有约束应实现为任务队列中的任务类型，不新增常驻服务。
3. **做深 Agent 工具层**：见第五节的 5.1、5.2、5.3。
4. **以评测结果驱动检索增强**：见第五节的 5.5 之后各项。

## 五、值得扩展的研究功能

评估标准：是否对准已知短板；是否符合“不新增常驻服务、不在进程内加载模型、改动必须附评测对比”的约束；成本是否可控。

### 5.1 MCP 用户委托授权（优先级：高）

- **研究与标准动态**：MCP 授权规范已采用 OAuth 流程，并要求客户端在授权与令牌请求中携带资源参数（RFC 8707），支持按需提升权限范围（见 [MCP 授权规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)）。
- **现状差距**：TuskRAG 的 MCP 只支持 API Key。一个 Key 代表一个固定主体，Agent 无法“以当前提问用户的身份”检索，文档级权限在 Agent 场景下会退化为 Key 级权限。
- **建议**：让 `/mcp` 作为 OAuth 资源服务器，复用已有的 OIDC 身份与用户组映射，令牌主体进入现有的主体标签计算。这是把 2.2 的权限优势延伸到 Agent 场景的必要条件。
- **代价**：令牌校验与受众检查的实现和安全测试；不需要新服务。

### 5.2 检索投毒与间接提示注入防护（优先级：高）

- **研究动态**：PoisonedRAG 一类工作表明，针对单个目标问题注入少量文本即可操纵回答；防御研究转向多层方案，包括入库扫描、证据一致性校验和来源证明（见 [EmbedGuard](https://zenodo.org/records/23032135/files/EmbedGuard-manuscript-v3.2.pdf?download=1) 及其综述部分）。视觉检索路径上还出现了经 OCR 文本绕过过滤的问题。
- **现状差距**：TuskRAG 的解析安全针对恶意文件（炸弹、实体注入），没有针对“内容本身是攻击指令”的防护。一旦接入连接器和 URL 导入，知识库内容的可信度会下降。
- **建议**，按成本从低到高：
  1. 来源可信分级：按知识库或文档标记可信等级，进入证据元数据和审计。
  2. 入库时的注入模式扫描，命中进入待审而非静默入库；扫描同时覆盖原生文本与 VLM 重解析文本。
  3. MCP 工具返回中明确把证据标为“数据”，并附来源等级，方便外部 Agent 采取相应策略。
  4. 评测集增加投毒与注入题型，作为门禁的一部分。
- **契合度**：与“权限可证明、失败显式”的品牌一致，并且大多不需要模型调用。

### 5.3 Agentic 检索的停止、路由与工具扩展（优先级：高）

- **研究动态**：Agentic RAG 与深度研究已成为主流研究方向（见 [ACL 2026 综述](https://aclanthology.org/2026.findings-acl.78/)、[AACL 2026 教程](https://aclanthology.org/2026.aacl-tutorials.5/)）；以目录树推理替代向量检索的方案（[PageIndex](https://pypi.org/project/pageindex/)）在长结构化文档上受到关注；代码 Agent 领域出现了以精确匹配工具替代向量检索的做法。
- **现状差距**：见 3.5，循环全部跑满步数上限。
- **建议**：
  1. 先修停止判断：证据充分性自检，或在工具结果无新增证据时提前收束。以 E7 的截断率和耗时作为回归指标。
  2. 复杂度路由：文档中已设计“复杂问题自动升级”，应以评测数据决定是否启用，并扩充跨文档题集（当前只有 4 题）。
  3. 增加精确匹配工具：面向条款号、编号、错误码的正则或子串检索。可以基于 PG 的三元组索引实现，不引入新组件。
  4. 把“目录导航式检索”作为长文档（合同、手册、标准）的卖点来评测。TuskRAG 已有目录与读节工具，这是现成的结构优势。

### 5.4 评测闭环：自动出题与线上反馈回流（优先级：高）

- **研究动态**：生产级 RAG 评测框架趋向多维度，同时覆盖引用质量、延迟成本、证据忠实度、答案相关性和检索质量（见 [CLEAR-RAG](https://zenodo.org/records/20110205)）；企业场景的基准也在出现（如 EnterpriseRAG-Bench，见 [haiku.rag 基准记录](https://github.com/ggozad/haiku.rag/blob/27e7f63af0ef970fc2cddc2e374a498e6117d748/docs/benchmarks.md)）。
- **现状差距**：题集靠人工维护；反馈进入待审池，但没有形成“差评 → 题集 → 回归”的固定流程；评测报告中成本维度较弱。
- **建议**：
  1. 从客户语料自动生成候选题与无答案题，人工确认后入题集。这直接缓解 3.2 的真实语料不足。
  2. 差评与纠错一键转为题集条目。
  3. 报告增加每题成本与 token 用量，配置对比时同时看质量与成本。
  4. 把“入场评测 + 验收报告”做成标准交付物。
- **代价**：出题需要调用 LLM，受出域策略约束；全部可用现有任务队列实现。

### 5.5 Contextual Retrieval（优先级：中，先做实验）

- **研究结论**：Anthropic 报告称，上下文化嵌入加上下文化 BM25 使前 20 块的检索失败率降低 49%（5.7% → 2.9%），叠加重排后降低 67%（见 [Contextual Retrieval](https://www.anthropic.com/research/contextual-retrieval)）。
- **与现状的关系**：TuskRAG 用“标题路径前置”实现了零模型成本的近似方案，并且已有可选的节摘要。E3 在合成题集上显示标题路径的增益有限，但该题集过小。
- **建议**：作为知识库级的可选项做对照实验，把节摘要或块级上下文说明写入检索文本。只有在真实语料上有稳定增益才进入路线，这与现有的非目标条款一致。
- **代价**：入库时每块一次 LLM 调用，成本和入库时长上升，内容需要出域许可。

### 5.6 视觉文档检索与多模态证据（优先级：中）

- **研究动态**：以页面图像做延迟交互检索的 ColPali / ColQwen 系列是文档检索的活跃方向，ViDoRe 基准已迭代到第三版；也有工作指出纯视觉检索与生成之间存在落差，倾向于视觉检索与 OCR 文本结合（见 [ViDoRe 相关论文](https://export.arxiv.org/pdf/2610.27829)、[AnchorFold](https://arxiv.org/html/2608.08732v1)、[ColPali-Fusion++](https://zenodo.org/records/20549254/files/MRAG_Research.pdf?download=1)）。
- **与现状的关系**：对准“复杂版面、图表、扫描件”这一已承认的短板。
- **约束**：多向量索引的存储量是单向量的数十到上百倍，pgvector 没有原生的延迟交互算子，全量采用会破坏“轻”。
- **建议**，分两步：
  1. 低成本路径：对质量门判为低分的页面，在问答时把页面图像作为证据交给多模态模型，并支持图像区域引用。不改索引。
  2. 实验路径：只对低分页生成页级视觉向量，作为第三路召回并入 RRF。先在含图表的评测集上验证增益再决定。

### 5.7 表格与结构化数据问答（优先级：中）

- **动机**：企业文档中表格密度高；对 XLSX、CSV 做分块后检索，回答聚合类问题（求和、筛选、对比）效果天然不好。
- **优势**：数据本来就在 PostgreSQL 中，把确认过表头的表格落为受控的只读关系并用受限 SQL 查询，不需要新组件。
- **风险**：SQL 生成的安全边界（只读、限行、限时、权限继承）必须先设计清楚；需要专门的表格题集。

### 5.8 规模与向量索引演进（优先级：中，按触发条件）

- **动态**：pgvector 的迭代扫描缓解了过滤查询的召回问题，但更大规模下索引构建内存和过滤取舍会推动团队转向 VectorChord 等方案（见 [pgvector 概览](https://whichdb.com/pgvector)）。EDB 发布的对比称 VectorChord 的单客户端吞吐为 pgvector HNSW 的 13.4 倍（见 [EDB 基准](https://edb.prod.acquia-sites.com/sites/default/files/2026-06/pgvector_vs_VectorChord_benchmarks.pdf)）。这是厂商基准，需要自行复测。
- **与现状的关系**：百万块 p95 未达标（3.3）。[A04](../11-架构决策记录.md#a04) 已写明重审条件。
- **建议**：在出现百万块以上的真实客户前不投入；届时把量化加精排、VectorChord 作为候选进行同口径对比，并先核实许可。

### 5.9 GraphRAG 类能力（优先级：低，保持观望）

- **动态**：LazyGraphRAG 把索引成本降到完整 GraphRAG 的约 0.1%，把图构建推迟到查询时（见 [介绍](https://developer.aliyun.com/article/1642350)）。
- **判断**：全局总结类问题在企业问答中的占比尚无 TuskRAG 自己的数据。先在题集中加入“跨文档汇总”题型并观察 Agentic 模式的表现；只有在该类问题占比高且 Agentic 模式不足时才考虑。

### 5.10 Late Chunking（优先级：低）

依赖嵌入服务端的支持，而 TuskRAG 的模型全部外置；公开的增益主要在方法提出方自己的模型上验证（见 [Jina 的说明](https://jina.ai/news/late-chunking-in-long-context-embedding-models/)）。等待主流嵌入接口普遍支持后再评估。

### 5.11 优先级汇总

| 优先级 | 项目 | 对准的问题 | 是否需要模型调用 |
|---|---|---|---|
| 高 | 连接器与源端权限同步（4.4） | 数据接入 | 否 |
| 高 | MCP 用户委托授权（5.1） | Agent 场景下的权限退化 | 否 |
| 高 | 投毒与注入防护（5.2） | 内容可信度 | 基本不需要 |
| 高 | Agentic 停止与路由、精确匹配工具（5.3） | E7 暴露的问题 | 是 |
| 高 | 评测闭环（5.4） | 真实语料证据不足 | 是 |
| 中 | Contextual Retrieval 实验（5.5） | 召回失败率 | 是（入库时） |
| 中 | 多模态证据与视觉召回（5.6） | 复杂版面与扫描件 | 是 |
| 中 | 表格结构化问答（5.7） | 聚合类问题 | 是 |
| 中 | 向量索引演进（5.8） | 百万块延迟 | 否 |
| 低 | GraphRAG 类（5.9）、Late Chunking（5.10） | 尚无需求证据 | — |

## 六、风险提示

1. **团队规模**：按 2 名全栈估算。第五节的高优先级项合计已超过一个里程碑的容量，需要在连接器与 Agent 工具层之间排序。本报告的建议是先连接器。
2. **定位漂移**：每增加一项检索增强都会增加入库成本和配置复杂度，侵蚀“轻”。坚持“评测证明增益才进入路线”的既有规则。
3. **许可**：AGPL 结论直接影响 OEM 方向（方向 B）。如果法务否决，兼容驱动成为默认，其质量损失需要在真实语料上重新量化。
4. **对外数字**：在第三节的缺口关闭之前，延迟、并发和准确率数字只能作为“特定条件下的实测值”引用，并附条件说明。
