# 11 架构决策记录

格式：决策 / 备选 / 理由 / 代价 / 重审条件。状态：**已采纳**（按此实施）或 **待定**（M0 Spike 后定案）。

<a id="a01"></a>
## A01 PostgreSQL 单栈（已采纳）

- **决策**：PG 17 是唯一的业务状态、全文检索、向量检索、任务队列与审计存储；不引入 Elasticsearch、Redis、MinIO、消息队列。
- **备选**：ES + MySQL + Redis + MinIO（RAGFlow 式）；Qdrant/LanceDB + SQLite（嵌入式极简栈）。
- **理由**：一个进程、一次备份、一个事务边界；权限过滤与版本切换可在同一事务中原子完成，这是嵌入式向量库 + 独立业务库很难做到的；企业 DBA 普遍熟悉 PG。
- **代价**：检索与业务争用同一实例资源；超大规模下不如专用搜索集群。
- **重审条件**：单库当前块 > 500 万；或检索 QPS 持续 > 200 且读副本无法满足；或 BM25 驱动无法满足评测门槛。

## A02 Go 核心单二进制 + Python 一次性解析工具（已采纳，2026-10-28 修订）

- **决策**：服务端主体使用 Go（API、SSE、MCP、鉴权与权限、检索编排、分块、分词、任务调度、模型调用、审计），单一静态二进制内嵌前端与迁移，以 `api`/`worker`/`all`/`migrate` 角色运行。Python 只作为文档解析工具 `tuskrag-parse`：无端口、无网络、无数据库、无状态，由 Go worker 按任务启动并在结束后退出；两侧唯一契约为 `contracts/parsed-document.schema.json`。
- **原则**：技术栈不得拖累产品质量——每个环节选“该环节质量最好”的语言；Python 仅限“工具”角色，不承担常驻服务、业务状态或策略判断。
- **备选**：
  - 全 Python（FastAPI）：v0.1 方案。常驻内存与并发 SSE 稳定性不如 Go，且要额外做子进程隔离来规避堆碎片；放弃。
  - 全 Go：Go 现有 PDF 版面/表格、DOCX 样式编号、HTML 正文抽取库在结构保真上明显弱于 pdfplumber、python-docx、trafilatura，直接损害“准”；放弃。
  - Go 核心 + 常驻 Python gRPC Worker（参考项目模式）：增加一个常驻服务、证书与 RPC 契约，而解析是低频任务，不值得常驻；放弃。
- **理由**：读路径（检索与问答）全部在 Go 内完成，常驻内存数十 MB、取消与超时贯穿、单二进制交付；解析质量保留 Python 生态优势，且一次性进程天然实现“用完即释放”与恶意文件隔离。
- **代价**：两种语言工具链（Go + Python 工具）；跨语言契约需版本化与测试；镜像需携带 Python 运行时（磁盘约 150—250 MB，不占常驻内存）。
- **重审条件**：Go 生态出现在评测样本上不劣于当前 Python 驱动的解析库 → 逐格式迁回 Go（每迁一种须过 E5 同类对比）；或解析吞吐需要常驻 Worker（单实例每日入库 > 10 万页）→ 再评估常驻服务形态。

## A03 BM25 采用双驱动：pg_search 默认，tsvector 兼容（已采纳，许可待法务确认）

- **决策**：默认 `pg_search`（ParadeDB，Jieba 分词，真 BM25）；兼容驱动为“Go 应用侧分词（gse，加载 jieba 格式词典）+ `tsvector('simple')` + GIN + `ts_rank_cd`”。两者实现同一 Go `LexicalDriver` 接口，由配置选择，启动时校验扩展存在。
- **备选**：只用 tsvector + zhparser/pg_jieba 扩展；VectorChord-bm25；外部 ES。
- **理由**：真 BM25 带 IDF，对中文术语与条款号召回更好；兼容驱动不需要任何非标准扩展，可运行在 RDS 等托管 PG，也规避 AGPL。
- **代价**：pg_search 为 AGPL-3.0；客户内网交付涉及分发条件，组件构成及相应源码义务须由法务确认（M0 门禁），详见 [许可证盘点](../deploy/licenses/README.md)。两套驱动增加测试面。
- **重审条件**：法务否决 AGPL → 兼容驱动成为默认，并评估 VectorChord-bm25 等替代（许可须先核实）；E4 显示兼容驱动降级 < 1 个点 → 可考虑只保留兼容驱动。
- **S1 初探**：固定 `pg_search` 0.22.6 的合成样例中，访问标签数组条件由扫描内堆过滤而非索引原生过滤；详见 [Spike 证据](../tests/spikes/README.md#s1中文分词与过滤计划初探)。规模性能、召回和许可仍待验证。
- **S1/V08 后续验证（2026-10-30）**：单知识库主体以数据库生成的 `kb_access` 表达原访问标签判断，授权当前版本及文档条件先形成版本集合，BM25 v2 在 Top-K 内过滤；普通相关 EXISTS 在该扩展版本中出现截断后过滤、漏掉可见候选，已由反例否决。原生召回事务关闭查询并行，以复用 Jieba 词典缓存；不放宽 RLS、模型出域或出库复核。20 万块 p95=84.978 ms，详细负载边界与百万块数据见 [云端容量报告](eval-reports/2026-10-30-sql-capacity.md)。这不代表通用 ACL、并发负载或真实模型全链路达标。
- **计划缓存安全约束**：固定版本在复用通用计划并改变租户上下文时可返回其他租户的行。应用连接强制 `force_custom_plan`，就绪检查拒绝不满足该设置的连接；检索事务还须本地设置该选项并复核权限。连接池代理及完整检索权限验收尚未验证，证据见 [索引对照](eval-reports/2026-10-28-index-provision.md)。

## A04 向量：pgvector halfvec + HNSW 部分索引（已采纳）

- **决策**：`chunk_vector.embedding halfvec`；每个嵌入空间一个 `WHERE space_id = X AND is_current` 的部分 HNSW 索引（cosine）；启用 `hnsw.iterative_scan = relaxed_order` 解决过滤后召回不足。默认嵌入模型 bge-m3（1024 维）。
- **备选**：vector(float32)；IVFFlat；VectorChord；外部向量库。
- **理由**：halfvec 内存减半且对检索精度影响很小（须 E 实验确认）；部分索引支持模型切换与多空间共存；0.8 起的迭代扫描专门解决带过滤的近邻搜索。
- **代价**：维度固定在索引表达式中；嵌入模型切换需重建（A05/T13 流程）。
- **重审条件**：E 实验显示 halfvec 损失 > 1 个点；或 100 万块下向量召回 p95 > 50 ms。
- **S2 初探**：10 万条 1024 维合成向量的单次过滤查询中，迭代扫描与精确 Top 20 一致；默认容器共享内存不足以完成该设置下的并行建索引，串行建索引成功。数据分布与结果局限见 [Spike 证据](../tests/spikes/README.md#s2过滤后的-hnsw-迭代扫描单次合成实验)；真实数据召回和性能仍待验证。
- **索引职责**：由一次性运维命令使用迁移角色并发创建共享 BM25 索引及每个嵌入空间的 HNSW 索引；应用角色不获得 DDL 权限。建索引会占用数据库 CPU、内存、磁盘与维护连接，并按运维命令串行化；失败可能留下无效索引，必须显式检查后修复。应用须在发布版本前核验索引定义和有效性。当前实现只接受 cosine；内积空间在对应索引与检索契约验证前显式拒绝。

## A05 模型全部外置，统一 OpenAI 兼容接口（已采纳）

- **决策**：LLM、嵌入、重排、VLM 均通过 HTTP 调用（`/v1/chat/completions`、`/v1/embeddings`、`/v1/rerank`，重排请求体兼容 Jina/Cohere 风格）；提供方 BaseURL 为版本路径之前的根地址。2026-10-29 依据 SiliconFlow 实际接口统一重排版本前缀，避免与嵌入配置语义不一致。核心镜像不包含推理框架与模型权重。离线部署使用独立模型节点（vLLM / TEI / Xinference 等）。
- **备选**：进程内 ONNX（FastEmbed）；Ollama 同机。
- **理由**：常驻内存与模型完全解耦；并发由模型网关承担；模型升级不需要重发核心镜像。FastEmbed 官方支持列表不含 bge-m3 与 bge-reranker-v2-m3，且同机加载两者至少需 1.2 GB（INT8）以上，与“轻”冲突。
- **代价**：多一跳网络延迟；依赖外部可用性（以显式失败与降级标注处理）。
- **重审条件**：客户要求单机全离线且无独立模型节点 → 提供“同机模型服务”部署档位（仍是独立进程，不进核心）。

## A06 分层解析：原生优先 + 页级质量门 + 按需 VLM（已采纳）

- **决策**：默认使用宽松许可的原生解析库（pypdfium2、pdfplumber、python-docx、python-pptx、openpyxl/calamine、trafilatura，均在 `tuskrag-parse` 工具内）；逐页质量评分（工具报告信号、Go 判定），低分页才送 VLM；不常驻 LibreOffice/Playwright/本地 OCR；旧版 Office 格式默认拒绝，可选一次性转换容器。
- **备选**：全量走 MinerU/Docling 等深度版面模型；PyMuPDF4LLM；全量 VLM。
- **理由**：多数企业文档是数字原生，原生解析快且无成本；页级而非文档级送 VLM 控制成本与出域范围；PyMuPDF 系为 AGPL/商业双许可，不宜作为默认依赖。
- **代价**：复杂版面（多栏、无线表）在原生路径上质量有限，依赖质量门识别；质量门阈值需要样本校准。
- **重审条件**：E5 显示原生路径在客户样本上表格/多栏错误率过高 → 引入独立的版面解析服务（作为模型节点上的按需服务，不进核心）。

<a id="a07"></a>
## A07 解析在一次性子进程中执行（已采纳）

- **决策**：Go worker 每个任务启动一次性受限解析进程：Markdown/TXT 使用同一 Go 二进制的内部解析子命令，其他已支持格式使用 `tuskrag-parse`。两条路径均带内存/CPU/墙钟限额、无网络、只读输入与独立临时目录；超时或取消时杀整个进程组；输出过 schema 与大小校验后才被使用。Go 二进制通过只读文件描述符绑定，文件替换后工作进程须重启。
- **理由**：真正实现“解析完即释放”；解析库的崩溃、内存泄漏或恶意文件只影响一次性子进程，Go 常驻进程不受影响。
- **代价**：每任务启动进程的开销尚待测量；Windows 与 Linux 分别需要隔离实现。Go 运行时需较大的虚拟地址预留，Linux 对 Go 子进程使用 cgroup v2 控制实际内存，而非 `RLIMIT_AS`；同样限制整个进程树。
- **重审条件**：批量小文件入库吞吐不足 → 允许子进程处理同一批次的多个小文件后退出（上限可配）。

<a id="a08"></a>
## A08 结构化父子分块 + 标题路径（已采纳）

- **决策**：按标题树分节，节为父块，节内 300—500 token 子块；`search_text` 前置标题路径；表格整体或带表头切分；检索命中后父节回溯。
- **备选**：固定长度滑窗；语义分块（嵌入相似度切分）；GraphRAG；Contextual Retrieval 默认开启。
- **理由**：企业制度、手册、技术文档的结构本身就是最强的语义边界；标题路径以零模型成本补充上下文。
- **代价**：依赖解析出的标题结构；无结构文本退化为段落聚合。
- **重审条件**：E3 未显示优于固定长度分块。

<a id="a09"></a>
## A09 RRF 融合 + 交叉编码重排 + 校准阈值拒答（已采纳）

- **决策**：BM25 Top50 ∥ 向量 Top50 → RRF(k=60) → Top30 重排 → 阈值；阈值由评测集无答案题校准。
- **备选**：加权分数线性融合；只用重排；LLM 重排。
- **理由**：RRF 不需要对两路异构分数做归一化，稳健；交叉编码器是性价比最高的精度来源；LLM 重排延迟与成本过高。
- **重审条件**：E1/E2 显示其他融合方式稳定更优。

<a id="a10"></a>
## A10 默认单轮检索，Agentic 为显式模式（已采纳）

- **决策**：标准问答单轮检索；Agentic（工具循环：search / get_toc / read_section / get_neighbors）需显式开启或按规则升级；外部 Agent 通过 MCP 自行编排。
- **理由**：多数问题单轮即可回答；Agentic 的多次 LLM 调用与“快”冲突，只应花在需要的问题上。
- **重审条件**：E7 显示跨文档题占比高且 Agentic 增益显著 → 调整自动升级规则。

<a id="a11"></a>
## A11 权限：RLS 租户隔离 + access_tags 预过滤 + 出库复核（已采纳）

- **决策**：RLS 只做租户隔离；知识库角色与文档 ACL 反范式化为 `access_tags`，在召回 SQL 中预过滤；结果出库前按当前 ACL 复核。
- **备选**：召回后过滤；每次查询 JOIN ACL 表。
- **理由**：预过滤保证 TopK 不被无权结果挤占；复核覆盖反范式化字段的刷新窗口，满足“撤权即时生效”。
- **代价**：ACL 变更需要异步刷新大量块（批量 UPDATE）；超大 restricted 主体列表会使数组变大（上限：单文档 ≤ 200 个主体，超出须用组）。

<a id="a12"></a>
## A12 任务队列基于 PG（自研，已采纳）

- **决策**：自研普通表 + `FOR UPDATE SKIP LOCKED` + 租约世代 + `LISTEN/NOTIFY` 唤醒；语义见 [04 第八节](04-数据模型与存储.md#八任务队列)。认领与提交必须在数据库事务中校验世代；worker 已接入受限入库和旧版本清理，完整 V02 尚未通过。
- **依据**：S3 在 PostgreSQL 上以两个真实 River 0.49.0 worker 和一次模拟救援复现：第二轮执行已开始时，第一轮仍可用 `JobCompleteTx` 提交副作用并完成任务，未直接满足 V02。可以为 River 另建围栏机制，但仍需自行协调认领与副作用事务；自研统一队列表更直接。详见 [Spike 证据](../tests/spikes/README.md#s3river-迟到提交)。
- **代价**：需自行实现并测试租约续期、重试、去重、取消、死信与可观测；River 的其他能力本次未完整评估。
- **重审条件**：成熟上游可在相同租户隔离和事务边界内证明单调世代、迟到提交拒绝与 V02 全部通过。
- **不采用**：UNLOGGED 表做队列；Redis/NATS 等外部队列。

## A13 前端沿用参考项目规范，由 Go 内嵌托管（已采纳）

- **决策**：React + Vite + TS + shadcn/ui + Tailwind，Vercel 风格；Go 核心经 huma 从类型生成 OpenAPI，前端生成类型客户端；静态产物 `go:embed` 进二进制，生产不运行 Node。详见 [08](08-前端架构与交互.md)。

<a id="a14"></a>
## A14 不使用 LangChain / LlamaIndex / LangChainGo 等编排框架（已采纳）

- **决策**：检索、融合、组装、生成编排自行实现（薄、可测、可追踪）；只使用具体功能库（解析、分词、HTTP 客户端、MCP SDK）。
- **理由**：框架抽象层厚、版本变动快、行为不透明，不利于调试“为什么没召回”；本系统的流水线固定且简单。
- **重审条件**：出现大量需要复用的框架能力且自研成本显著。

<a id="a15"></a>
## A15 文件存储：本地盘默认，S3 兼容可选（已采纳）

- **决策**：`FileStore` 驱动接口；默认挂载卷；企业已有对象存储时用 s3 驱动；不自带 MinIO。原件不入 PG（避免库膨胀与备份变慢）。
- **重审条件**：多节点 worker 无共享盘且无对象存储 → 要求部署 NFS 或对象存储，不在核心中实现复制。

<a id="a16"></a>
## A16 数据出域按知识库策略强制执行（已采纳）

- **决策**：提供方声明 `internal/external`；知识库 `egress_policy` 决定可用提供方；所有模型调用经 `models` 单入口检查。详见 [07 第六节](07-权限安全与企业治理.md#六数据出域策略)。
- **理由**：VLM OCR、LLM 都会把正文发出去；必须是可审计的显式策略，而不是部署者的默认习惯。
