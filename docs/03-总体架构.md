# 03 总体架构

> 完整的分域 Mermaid 架构图（含后端包依赖、入库流水线、检索/Agentic/MCP 双读路径与权限纵深防御）见 [架构图解](架构图解.md)。

## 一、总览

```text
                ┌──────────── 使用者 / 管理员（浏览器 SPA）
                │      ┌───── 外部 Agent（MCP Streamable HTTP / REST + API Key）
                ▼      ▼
        ┌──────────────────────────────────────────────────┐
        │ tuskrag  (Go 单二进制，内嵌 SPA，按角色启动)          │
        │  role=api    : HTTP API · SSE · MCP · 静态 SPA     │
        │  role=worker : 入库/重建/清理/评测任务                │
        │  role=all    : api + worker（lite 档位）            │
        └──────┬───────────────┬───────────────┬─────────┬──┘
               │ SQL(pgx v5)   │ 文件读写        │ HTTPS   │ 按任务 spawn，结束即退出
               ▼               ▼               ▼         ▼
   ┌────────────────────┐ ┌──────────────┐ ┌──────────┐ ┌───────────────────────────┐
   │ PostgreSQL 17      │ │ FileStore    │ │ 模型提供方 │ │ tuskrag-parse（Python 工具）│
   │ · 业务表 + RLS      │ │ 本地盘 / S3   │ │ LLM·Emb· │ │ 一次性子进程：文件 → 结构化  │
   │ · pgvector(halfvec)│ │ 兼容对象存储  │ │ Rerank·VLM│ │ JSON；无网络、无常驻、受限额 │
   │ · pg_search(BM25)  │ └──────────────┘ └──────────┘ └───────────────────────────┘
   │ · 任务队列(SKIP LOCKED)│
   └────────────────────┘
```

常驻进程只有 PostgreSQL 与 tuskrag（Go）。FileStore 默认是本地挂载盘；企业已有对象存储时通过驱动接入，不自带 MinIO。模型服务永远是外部依赖。

## 二、语言分工：Go 为主，Python 只作解析工具

技术栈服务于产品质量，按“谁在该环节质量更好”分工（[A02](11-架构决策记录.md#a02)）：

| 环节 | 语言 | 理由 |
|---|---|---|
| API、SSE、MCP、鉴权与权限、检索编排、融合与组装、任务调度、模型调用、审计 | **Go** | 常驻内存小（数十 MB）、高并发 SSE 稳定、单二进制交付、强类型与 context 取消贯穿全链路；这些环节决定“快、轻、稳” |
| 分块、中文分词（兼容驱动与查询分析）、引用校验 | **Go** | 纯算法，Go 实现无质量损失，且与检索在同一进程，避免跨进程往返 |
| 文档解析（PDF 版面/表格、DOCX、PPTX、XLSX、HTML 正文抽取）、PDF 页面渲染 | **Python 工具** | pdfplumber、pypdfium2、python-docx、trafilatura 等在结构保真上明显优于 Go 现有库；解析质量直接决定“准”，因此保留 Python，但只以**一次性 CLI 子进程**形态存在 |

Python 工具不是服务：无端口、无网络、无数据库连接、无状态；由 Go worker 按任务启动，读输入文件、写结构化 JSON、退出。Go 与 Python 之间只有一个契约：`contracts/parsed-document.schema.json`（JSON Schema，两侧都校验）。

## 三、进程角色

| 角色 | 职责 | 状态 | 扩展方式 |
|---|---|---|---|
| `api` | 鉴权、REST、SSE 问答、MCP、检索编排、静态 SPA 托管 | 无状态 | 水平多实例，前置任意 L7 负载均衡 |
| `worker` | 认领入库/重建/清理/评测任务；启动解析子进程；分块；调用嵌入/VLM；写索引 | 无状态（任务状态在 PG） | 水平多实例；每实例并发度可配 |
| `all` | 同进程运行 api + worker | 同上 | 仅单机 lite 档位 |
| `migrate` | 执行数据库迁移后退出 | 一次性 | 部署流程中先于其他角色运行 |

同一二进制，通过 `TUSKRAG_ROLE` 选择；启动时校验 PG 版本、扩展、迁移版本、驱动能力、解析工具版本与配置，不满足即拒绝启动。

## 四、核心链路

### 4.1 入库（写路径，低频、可慢、可重试）

```text
上传 → 存原件(FileStore) + 建 document_version(status=queued) + 入队 ingest 任务   [同一事务]
Go worker 认领(租约) → spawn tuskrag-parse（限额）→ ParsedDocument JSON（校验 schema）
→ Go 页级质量门 → [低分页 → spawn tuskrag-parse render 出页图 → Go 调 VLM（受出域策略约束）]
→ Go 分节/分块 → 批量嵌入(外部) → 写 section/chunk/chunk_vector(is_current=false)
→ 单事务切换 current_version、刷新 access_tags、旧版本 superseded → status=ready
```

### 4.2 检索与问答（读路径，高频、要快）

```text
鉴权 → 解析主体集合(用户/组/角色 → principal tags) → [多轮：问题改写]
→ 查询嵌入(外部, 有缓存) → 单条 SQL：预过滤 + BM25 TopK ∥ 向量 TopK → RRF
→ 重排 TopN(外部) → 阈值判定 → 父节回溯/相邻合并/打包 → 出库复核当前权限
→ [检索 API 直接返回] 或 [LLM 生成(SSE) → 引用校验 → 存会话/引用]
```

读路径全部在 Go 进程内完成，不经过 Python。

## 五、后端模块划分

Go 模块 `services/core`，领域包位于 `internal/`，包之间只通过公开接口调用，不直接改写其他模块的表（[架构规则](../.agents/rules/architecture.md)）。

| 包 | 拥有的状态 | 对外提供 |
|---|---|---|
| `identity` | 租户、用户、组、成员、会话、API Key、OIDC 配置 | 当前主体与 principal tags 解析 |
| `kb` | 知识库、成员角色、配置修订、文档、版本、ACL | 权限判定、文档生命周期 |
| `ingest` | 入库任务进度、解析报告 | 解析工具调用与限额、质量门、分块器 |
| `index` | section、chunk、chunk_vector、嵌入空间 | 写入/切换/重建；Lexical 驱动与 Vector 驱动 |
| `retrieval` | 查询嵌入缓存（可丢失） | 混合召回、融合、重排、上下文组装 |
| `answer` | 会话、消息、引用、反馈 | 问答编排、引用校验、Agentic 循环 |
| `mcp` | 无 | MCP 工具适配（复用 retrieval/kb 服务） |
| `models` | 模型提供方配置、用量 | LLM/Embedding/Rerank/VLM 统一客户端、出域检查、限流与超时 |
| `storage` | 文件对象 | FileStore 驱动（local、s3） |
| `jobs` | 任务队列 | 入队、认领、租约、重试、死信 |
| `audit` | 审计日志 | 追加写与查询 |
| `eval` | 评测集、运行、结果 | 离线评测与对比 |
| `ops` | 无 | 健康、就绪、指标、诊断 |
| `httpapi` | 无 | 路由、请求解析、错误映射、SSE、SPA 托管（只调用领域服务） |

依赖方向：`httpapi/mcp → 领域服务 → 驱动接口 → 具体驱动`；领域包之间单向依赖（`answer → retrieval → index/kb/identity`），禁止循环（Go 编译器保证无环导入，另用 depguard 规则限制跨层导入）。

Python 工具 `services/parser`：包 `tuskrag_parser`，按格式划分驱动，统一输出 `ParsedDocument`；无数据库、无网络依赖（CI 中以无网络沙箱运行测试）。

## 七、仓库结构（Monorepo）

```text
TuskRAG/
  AGENTS.md                 # 执行约定
  .agents/                  # rules / skills / NOTES
  docs/                     # 本文档集
  apps/web/                 # React SPA（页面、业务组件、路由）
  packages/ui/              # shadcn/ui 基础组件、通用组合、主题 Token
  packages/api-client/      # 由 contracts/openapi.json 生成的类型 + 薄请求封装
  packages/config/          # 共享 tsconfig / biome 配置
  contracts/                # openapi.json、parsed-document.schema.json、mcp-tools.json、sse-events.json
  services/core/            # Go：cmd/tuskrag、internal/<包>、migrations、queries（sqlc）
  services/parser/          # Python 解析工具：src/tuskrag_parser、tests、样例文件
  deploy/                   # postgres 镜像、compose 档位、配置样例、运维脚本
  tests/e2e/                # Playwright 端到端
```

前端 pnpm、Go modules、Python uv 各自锁文件。构建顺序：前端静态产物 → `go:embed` 进核心二进制；解析工具打包为独立目录（Python 运行时 + 锁定依赖）随应用镜像分发。生产不运行 Node。

## 八、资源预算（lite 档位，目标值）

| 部件 | 常驻 | 峰值 | 控制手段 |
|---|---|---|---|
| PostgreSQL | 约 700 MB（`shared_buffers=512MB` + 进程开销） | 约 1.2 GB（索引构建） | 连接池上限、`work_mem`、维护窗口建索引 |
| tuskrag（Go，api + worker） | 40—80 MB | 约 200 MB（高并发 SSE + 嵌入批次） | `GOMEMLIMIT`、流式响应不缓存全文、批次上限 |
| 解析子进程（Python） | 0（空闲时不存在） | ≤ 600 MB（单任务限额） | 每任务新进程、超时与内存上限、结束即释放 |
| 模型 | 0（外置） | 0 | — |
| 合计 | **≈ 0.75—0.8 GB** | **≈ 2.0 GB** | 留出 OS 页缓存给 PG |

数字为设计预算，以 T17/V09 测量为准；偏差超过 20% 时更新本表并评估是否调整档位。

## 九、关键边界

1. 长计算（解析、嵌入、重排、LLM）不持有数据库事务；状态推进在短事务中完成。
2. 外部模型与解析工具的输出都视为不可信输入：ParsedDocument 先过 schema 与上限校验；模型结构化输出须校验；引用须对照证据集合。
3. 任何“无结果”必须区分：真的没有匹配 / 被权限过滤 / 依赖失败。三者在 API 中是不同状态（[13](13-接口契约概要.md#四错误模型)）。
4. 驱动能力在启动时声明并校验；不支持的能力拒绝启动或在响应中显式标注降级，不静默切换路径。
5. `context.Context` 贯穿请求链：客户端断开、超时、撤权都要能取消上游模型调用与解析子进程。
