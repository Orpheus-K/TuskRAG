# 09 部署运维与可观测

## 一、部署档位

下表是部署目标与对应编排入口。当前仓库已提供：
- Compose 容器编排与镜像定义（[Dockerfile](../deploy/Dockerfile)、[lite](../deploy/compose/docker-compose.lite.yml)、[standard](../deploy/compose/docker-compose.standard.yml)、叠加 [model-node](../deploy/compose/docker-compose.model-node.yml) 与 [legacy-office](../deploy/compose/docker-compose.legacy-office.yml)）
- Linux amd64 二进制打包、systemd 服务与冷备份恢复脚本（[Linux 交付](../deploy/linux/README.md)）
- 锁文件校验与 SBOM 生成脚本（[sbom.sh](../deploy/linux/sbom.sh)）及 Prometheus 告警模板（[prometheus-alerts.yml](../deploy/compose/prometheus-alerts.yml)）

HA 多主从副本（Patroni）、在线增量/WAL PITR、S3 对象备份及 Windows 完整解析沙箱仍未交付；表内资源与在线会话数仍为目标容量规划，需在对应环境实测确认。

| 档位 | 拓扑 | 适用 | 资源（目标） |
|---|---|---|---|
| lite | `postgres` + `tuskrag(role=all)`，单机 Docker Compose | ≤ 20 万块、≤ 50 在线会话、模型外置 | 2 vCPU / 4 GB / 40 GB SSD |
| standard | `postgres` + `tuskrag-api ×1..N` + `tuskrag-worker ×1..N` | ≤ 100 万块；入库与问答相互隔离 | 4 vCPU / 8—16 GB / 200 GB NVMe |
| ha | PG 主 + 同步/异步副本（Patroni 或托管 PG）+ api 多实例 + worker 多实例 | 生产高可用 | 按容量规划 |
| +model-node（可叠加） | 独立 GPU/CPU 节点运行 vLLM（LLM、VLM）与 TEI/Xinference（嵌入、重排），OpenAI 兼容 | 内网/离线 | 与核心节点分离，按模型规格 |
| +legacy-office（可叠加） | 一次性 LibreOffice 转换容器，由 worker 按任务启动 | 需要 DOC/PPT/XLS | 仅转换期间占用 |

只读副本可用于检索（读路径）以分担主库；写路径与任务队列只走主库。读副本复制延迟可能导致刚就绪的版本短暂不可见，在文档中说明，不影响权限（撤权以主库复核为准，见 [07](07-权限安全与企业治理.md#三检索时的权限执行)）。

## 二、制品

| 制品 | 内容 |
|---|---|
| `tuskrag-postgres:<pg>-<pgvector>-<pg_search>` | 官方 PostgreSQL 17 + pgvector + pg_search；固定版本与摘要；附带初始化脚本（角色、扩展） |
| `tuskrag:<version>` | Go 静态二进制（内嵌前端产物与迁移文件）+ 解析工具目录（Python 运行时与锁定依赖，仅按任务调用）；非 root 运行；只读根文件系统 + 可写临时卷 |
| 离线包 | 两个镜像 tar + compose 文件 + 配置样例 + SBOM（CycloneDX，覆盖 Go / Python / 前端依赖）+ 校验和 |

构建使用锁文件（`go mod download` 校验 go.sum、`uv sync --locked`、`pnpm install --frozen-lockfile`），生产不在线下载依赖或模型。当前提供 Linux Go 静态二进制 + 已构建解析运行时的打包脚本；完整离线镜像包和传递依赖 SBOM 仍是发行目标。

## 三、PostgreSQL 参考配置

lite（4 GB 主机，PG 预算约 1.5 GB）：

```ini
shared_buffers = 512MB
effective_cache_size = 2GB
work_mem = 16MB
maintenance_work_mem = 256MB      # 重建 HNSW 时会话级临时调到 1GB，在维护窗口进行
max_connections = 60
max_parallel_workers_per_gather = 1
jit = off
random_page_cost = 1.1
wal_compression = on
shared_preload_libraries = 'pg_search'   # 默认驱动需要；兼容驱动不需要
```

standard（16 GB 主机）：`shared_buffers=4GB`、`effective_cache_size=10GB`、`work_mem=32MB`、`maintenance_work_mem=1GB`、`max_parallel_workers_per_gather=2`。

内存安全公式（启动检查给出告警）：`shared_buffers + max_connections × work_mem × 2 + maintenance_work_mem ≤ PG 内存预算`。

## 四、备份与恢复

- 当前实现单机 local 冷备份：停止全部应用与外部写入后，先校验存储，再成对保存 `pg_dump -Fc` 和原件归档；以校验和与最终完成标记防止把中断产物当作备份。只记录 PG 快照时间、同时允许文件删除，不能保证成对一致性。
- `tuskrag ops verify-storage <tenant-id>` 使用应用角色及租户 RLS，分页校验每个保留版本的规范 key、字节数、SHA-256 和原件存在性。未知租户、缺失或损坏均返回错误；命令只读，不自动修改版本状态。
- 恢复仅面向新空库和新文件目录，遇错停止；主密钥独立保管，恢复后还须核对权限、会话/反馈、业务表摘要和固定检索结果。具体命令与前置条件统一见 [Linux 冷备份与恢复](../deploy/linux/README.md#冷备份与恢复)。
- 嵌入向量随 PG 保存，恢复向量不重新调用模型；恢复后的检索验证仍可能调用查询嵌入与重排模型。
- T16 每个发行版本执行；在线增量备份、WAL/PITR、S3 备份及自动调度尚未实现，不将本次冷备份演练扩展为这些能力。

## 五、升级与迁移

- 发布流程：`migrate` 角色先运行（只向前迁移），再滚动替换 api/worker。
- 迁移须兼容“新库 + 旧应用”至少一个版本（扩展 → 回填 → 切换 → 收缩），保证滚动升级期间不中断。
- 扩展升级（pgvector、pg_search）单独发布，附带索引重建说明与预计耗时；HNSW 使用 `CREATE INDEX CONCURRENTLY` 新建后切换。
- 在途任务：任务 payload 带 `schema_version`；worker 遇到不认识的版本拒绝认领，留给对应版本处理。
- 回退：只在迁移未进入“收缩”阶段前允许回退应用；已收缩则必须从备份恢复。

## 六、容量规划

1. 估算子块数：`文档数 × 平均块数`（M1 用真实样本统计平均块数）。
2. 热数据 ≈ 子块数 × 6 KB（[04 第六节](04-数据模型与存储.md#六容量估算)）；HNSW 索引 ≈ 子块数 × 2.4 KB 应尽量落在 `shared_buffers + OS 页缓存` 中。
3. 问答并发：api 每实例按 200 个并发 SSE 连接规划；实际上限受外部 LLM 的并发与 TPM 配额约束。
4. 入库吞吐：`worker 实例 × 每实例并发` 个子进程；嵌入批量吞吐受提供方限额约束。
5. 每个版本发布前用 V08/V09 复测，结果回写 [01 第三节](01-定位与范围.md#三量化目标目标值待测量) 与本节。

## 七、可观测

| 类型 | 内容 |
|---|---|
| 健康 | `/api/health/live`（进程存活）；`/api/health/ready`（PG 可连、迁移版本匹配、驱动能力、模型提供方最近探测状态） |
| 指标（Prometheus `/metrics`，需内网或 Token） | 请求延迟分位（按路由）、检索各阶段耗时、degraded 计数、重排/嵌入/LLM 调用延迟与错误、token 用量、队列长度与任务耗时、子进程峰值内存、PG 连接池使用率 |
| 日志 | JSON；字段：时间、级别、request_id、tenant_id、主体 ID、动作、耗时、结果码；禁止正文、Prompt、密钥 |
| 追踪（可选） | OpenTelemetry OTLP 导出，默认关闭；span 属性同日志限制 |
| 检索 Trace | 每次检索可保存（采样或调试模式）各阶段候选 ID 与分数，供调试台回看；保留 7 天 |

告警建议：ready 失败、队列积压 > 阈值、degraded 比例 > 5%、模型错误率 > 2%、PG 连接池使用率 > 80%、磁盘 > 80%。

## 八、运维命令

迁移完成后，可使用迁移角色的 `TUSKRAG_DATABASE_URL` 执行 `tuskrag provision-indexes <tenant-id> <space-id>`。命令在 PostgreSQL 17、pgvector 0.8.1、pg_search 0.22.6 上并发创建共享 BM25 索引和指定 cosine 嵌入空间的 HNSW 索引；重复执行会核验定义和状态。建索引期间占用数据库维护资源；其他同类命令等待。错误、命名冲突或中断遗留的无效索引不会自动删除，须先由数据库管理员核对定义和业务影响再修复。发布和单知识库混合召回会核验索引；评测与许可门禁见 [索引对照](eval-reports/2026-10-28-index-provision.md)。

迁移 19 增加从 `access_tags` 自动生成的 `chunk.kb_access`，并移除旧 BM25 v1 索引；v2 纳入当前版本号和该权限标志。在维护窗口停止 API/worker，执行迁移后，用迁移角色为各使用中的嵌入空间运行上述 `provision-indexes` 命令，再启动服务。生成列会重写块表，须预留磁盘和维护时间；新索引就绪前检索与发布显式失败。不要滚动混用要求 v1/v2 的程序版本。

人工修复索引须安排维护窗口，停止新的版本发布和索引管理命令，并确认在途事务结束后再操作；操作完成后重新运行索引命令验证。避免在版本发布期间由外部 DDL 绕过应用的协调锁。

当前 Linux 开发版可设置 `TUSKRAG_ROLE=worker` 或 `all`，并提供应用角色的 `TUSKRAG_DATABASE_URL`、原件目录 `TUSKRAG_STORAGE_DIR`、逗号分隔的 `TUSKRAG_WORKER_TENANTS`（1—64 个正整数），以及绝对路径 `TUSKRAG_PARSER`、`TUSKRAG_PARSER_RUNTIME_DIR`、`TUSKRAG_BUBBLEWRAP`、`TUSKRAG_CGROUP_ROOT` 和 `TUSKRAG_PARSER_TEMP_DIR`。`all` 还须设置 `TUSKRAG_LISTEN`；有加密模型凭据时提供 `TUSKRAG_MASTER_KEY_FILE`。启动时检查解析工具版本与隔离配置；运行时若隔离不可用则显式失败，要求见 [05 第七节](05-文档解析与入库.md#七工具隔离与限制)。每个工作进程串行处理已配置租户的 `ingest`、`purge`、`eval_run` 和 `reembed` 任务，连接池上限为 4，另有 1 条监听连接；其他任务类型保留在队列。生产部署与许可证门禁尚未完成。

已实现 `tuskrag ops verify-storage <tenant-id>`、`tuskrag ops diagnose <tenant-id>`（导出脱敏诊断快照：版本、扩展、词汇驱动与队列状态统计，不含正文与密钥）、`tuskrag ops rotate-master-key <tenant-id>`（通过 `TUSKRAG_OLD_MASTER_KEY_FILE` 与 `TUSKRAG_MASTER_KEY_FILE` 在单事务内重加密模型与 OIDC 凭据）及 `tuskrag ops reindex <tenant-id> --kb <kb-id>`（按知识库绑定嵌入空间校验/重建索引并执行 `ANALYZE chunk` / `ANALYZE chunk_vector`）；用法见 [部署手册](../deploy/README.md)。现有迁移入口为 `TUSKRAG_ROLE=migrate`。

监控端点 `GET /metrics` 已实现 Prometheus 文本格式导出（默认仅限回环地址访问，配置 `TUSKRAG_METRICS_TOKEN` 后需 Bearer 鉴权）。

开发验收使用[同机 Linux 进程测试入口](../tests/process/README.md)，先通过定向停机与隔离探测，再执行完整生产流程。此入口不替代部署和发布门禁。
